# MK09 2.0 の開発計画

状態: **計画 (まだ実装していません)**。2026-11-22 に、使う人からの方針を受けて作りました。
決めたことと、作る順序、各段階の作業と確かめ方を書きます。

## 1. 決めたこと

| 項目 | 内容 |
|---|---|
| 版 | 2.0 の開発中は `2.0.0preNNN` (NNN は 3 桁)。完成したら `2.0.0` |
| 機能 | (1) ファイル名の大文字・小文字の区別、(2) アカウント制のマルチユーザ (持ち主・主グループ・許可・パスワード)、(3) 同時に複数の端末 |
| 順序 | 大文字小文字 → アカウント制 → 複数端末 |

| 対象外 | **sbc09 の 64KB 版と FM-11 の Level 1 は 2.0 の機能を入れず、さわらない** (今までどおり 1.x の動き。出力が変わらないことを確かめる) |
| 大文字小文字 | 旧ディスク (大文字名) の探し直しの救済は入れない |
| グループ | 最初は主グループだけ |
| パスワード | 実際に使う |

## 2. 進め方の原則

### 2.1 「さわらない」の意味と、守り方
- 共有のソース (`fs_core.c`、`pm.c`、`sh.c` など) は、条件コンパイル (`MK09_V2`) の中で変えます。
- 64KB 版 (sbc09 の `build/`、FM-11 の Level 1) は、**変更の前後でビルドの出力 (イメージ、`.s19`) が同じバイト列**になることを確かめます。
  - 作業の最初に、1.46 の出力のチェックサムを `tests/v1.sha256` に記録します。
  - `tools/v1guard.sh` が、2 つの 1.x ビルドをやり直して、チェックサムを比べます。毎回の変更の前に実行します。
  - 1.x 側が (FM-11 の担当によって) 意図して変わるときは、その担当が記録を更新します。
- `MK09_V2` が有効になるのは、FM-11 Level 2 と sbc09 の MMU 版だけです (`LEVEL=2` の既定を、ビルドの変数で決める)。
- 起動の行と版は、1.x のビルドでは今までのままです (`MK09 1.46 ...`)。2.0 のビルドは `MK09 2.0.0pre001: kernel 2.0.0pre001 ...`。

### 2.2 版の規則
- **システム版** `MK09_VERSION`: コマンド、アプリケーション、カーネルのどれかが変わるたびに、`NNN` を上げます。
- **カーネル版** `MK09_KERNEL_VERSION`: カーネルが変わるときだけ上げます。
- 文書だけの変更では、どちらも上げません (1.x と同じ)。
- `TOOL_VERSION` (各コマンドの版) は、今までどおり別管理です。
- 履歴は、`version.h` と `DESIGN.md` の 16 章に、2.0 開発版の表を新しく足します (1.x の表は凍結)。

### 2.3 毎回の確認
1. `tools/v1guard.sh` (1.x のビルドが同じバイト列)。
2. 1.x のテスト (`make test`、`test_fm11.sh` の Level 1)。
3. 2.0 のテスト (FM-11 Level 2、sbc09 の MMU 版)。
4. `fsck.fat` でボリュームが正しいこと。

### 2.4 FM-11 の担当との分担
- 2.0 の開発中も、FM-11 の担当は 1.x の系列 (`fm11-port`) で作業を続け、私が master に取り込みます (いままでと同じ)。
- 取り込みで、共有のファイル (`kernel.s`、`version.h` など) が衝突しないよう、`MK09_V2` の中の変更は小さな単位にします。
- 2.0.0 に確定する**前に**、FM-11 の担当に、master (2.0 系列、`2.0.0pre`) の取り込みと、FM-11 の実機での確認を依頼します (確認の結果が出てから `2.0.0` に確定する)。

## 3. 段階

各段階の終わりに、`2.0.0preNNN` のどこまで進んだかを `version.h` の履歴に残します。

### 段階 0: 準備 (pre001)
- `MK09_V2` と、版の表示 (`2.0.0pre001`) を入れる (V2 のビルドだけ)。
- `tests/v1.sha256` と `tools/v1guard.sh`。
- 2.0 のテストを走らせる土台 (FM-11 Level 2 は既存の `test_fm11.sh` に V2 用の確認を足す)。
- 文書: `V2_PLAN.md` (この文書)、`DESIGN.md` の 16 章に 2.0 開発版の表。

### 段階 1: ファイル名の大文字・小文字の区別 (FM-11 Level 2 で先に)
- `to_name11` の大文字化をやめる (V2 のとき)。`dir_find` の 11 バイト完全一致はそのまま使えます。
- 名前の文字列を持つソースを、パスの定義 (`pathnames.h`) にまとめ、V2 は小文字 (`/bin/`、`.mx`、`/lib/clib.idx`、`/etc/rc.sh` ...)、1.x は今までの大文字にします。
  - 対象: `sh.c`、`pm.c`、`ccio.h`、`cpp.c`、`cg.c`、`cc1.c`、`as.c`、`pas0.c`、`pas1.c`、`time.c`、ほか。
  - `cc`、`pc`、`as` の拡張子の判定 (`.c`、`.pas`、`.s` など) も、小文字を前提にする。
- `tools/mkdisk.py` に、名前をそのまま (小文字で) 書くオプションを足す。V2 のイメージに使う。
- ホスト側のツールとテスト (`fatlib.py` の `find`、`mk09_test.py` の大文字のパス) は、V1 用と V2 用で、パスの大文字小文字を切り替えられるようにする。
- 副産物: Shift_JIS の漢字の 2 バイト目 (0x40-0x7E) が大文字化されて名前が壊れる問題が直る。
- 確かめ方: 大文字小文字だけが違う 2 つのファイルが共存できること。`fsck.fat -n` が通ること (小文字の短い名前は警告なしで通ることを確認済み)。

### 段階 2: アカウント制 (FM-11 Level 2 で先に)

**2a. 持ち主・グループ・許可の保存と検査 (FS)**
- ディレクトリエントリの、FAT16 で使われていない領域に入れる:
  - バイト 20: ユーザ番号 (0 は root)
  - バイト 21: グループ番号 + 1 (0 は「MK09 の情報なし」の目印。旧ファイルと PC のファイルは、root、標準の許可と見なす)
  - バイト 14-15: 許可 (持ち主・グループ・その他の `rwx` の 9 ビット、setuid などの予備)
- 検査: `open`、`mkdir`、`remove`、`rename`、`chdir`、`readdir`。ディレクトリでは通り抜けの `x` と、作成・削除に要る `w`。
- 新しい要求: `FS_CHMOD`、`FS_CHUSER` (持ち主とグループ)、`FS_STAT` に持ち主と許可を返す。`dirent_t` に 2 バイト足す。いまの `FS_CHOWN` (ハンドルの持ち主) は、名前を整理する。
- プログラムの読み込み (`FS_READTL`) は、起動する側のユーザで `r` と `x` を検査する。

**2b. ユーザの管理 (PM)**
- PM がタスクごとに (ユーザ、グループ) を持ち、起動時に親から引き継ぐ。PM は、起動のたびに FS へ通知する (FS はタスク番号ごとに覚え、終了時の `FS_CLOSEALL` で消す)。
- `PM_SETUID` (ユーザ・グループを変える): root のタスクだけに許す。
- シェルを一度終わらせて起こし直すとき (大きなプログラムのため) は、ユーザと現在のディレクトリを保つ。
- `kill` は、同じユーザか root だけ。`PM_SHUTDOWN` は root (またはグループ)。

**2c. ログインとパスワード (プログラム領域で動くので、サイズの制約なし)**
- `login`、`su`、`passwd`、`id`、`chmod`、`chown`、`chgrp`、`ls -l`。`ps` にユーザを出す。
- `/etc/passwd`、`/etc/group`、`/etc/shadow` (root だけ読める)。
- パスワードは、塩付きのハッシュ + 繰り返し。方式と繰り返し回数は、6809 で実測して決める (ログインの待ちが 1 秒程度)。
- `passwd` は、一時ファイルに書いてから名前を変えて置き換える (FAT には原子的な書き換えがない)。
- イメージを作るとき (`mkdisk.py`) に、初期のユーザ (root と一般のユーザ) と、そのハッシュを入れる。ホスト側にも、同じハッシュを計算するスクリプトを置く。

**2d. root 専用の操作**
`date -s`、`format`、`mount`、`umount`、`chown`、`shutdown`/`reboot`、他人のプロセスの `kill`。

確かめ方: ログイン、許可の拒否と許可、グループの許可、`su`、`passwd` の変更、他人の `kill` の拒否、`fsck.fat`。

### 段階 3: sbc09 の MMU 版 (2.0 では必須)
sbc09 (`sim09 -2` と Tang Nano 9K の `l2` モード) には、CoCo 3 風の MMU がある。MK09 に取り込む。

**調べたこと (2026-11-23)**
- **MMU**: 8KB のブロック 8 個 (論理 `$0000-$DFFF` と `$E000-$FFFF`) を、物理ブロック (0〜255 = 2MB) に割り当てる表が **2 つ** (システム `$FFA0-$FFA7`、ユーザ `$FFA8-$FFAF`)。使う表はタスクレジスタ `$FF91` のビット 0。割り込みで表が自動では切り替わらない (ソフトが切り替える)。
- **固定ページ**: `$FE00-$FFFF` はどの表でも物理 `$7FE00-$7FFFF` (割り込みベクタと I/O)。I/O は `$FF80` から (L1 の `$E000` と同じオフセット)。
- **起動**: `sim09 -2` は最初から L2 の機械。FPGA は L1 で始まり、ローダがモードレジスタ (`$E00E` に `$A2`) で L2 にして、ROM イメージを物理 `$7E000` に置き、`$A3` でリセットする (OS-9 L2 と同じ流れ。`os9/level2/l2boot.asm`、`tools/mkl2disk.py`)。MK09 もこの流れに乗せ、ROM イメージを MK09 用にする。
- **FM-11 Level 2 との違い**: FM-11 は 4KB × 16 ページの写像の組が **16 組** (タスクごとに 1 組。タスクを切り替えるときは、組の番号を 1 つ書くだけ)。sbc09 は **2 組** なので、ユーザのタスクを切り替えるたびに、ユーザの表の 8 個のレジスタを TCB から書き換える。他タスクのメモリを見る窓のレジスタ (FM-11 の `$FD91/$FD92`) もない: 窓は論理ブロックの 1 つを使う。
- カーネルの `ifdef MMU` は 26 か所 (`kernel.s`)。PM、MM、FS、TTY、DISK の `FM11_MMU` と、`bsp/fm11` の MMU 部分も対象。

**メモリの配置 (sbc09 の MMU 版)**
| 論理 | システム (サーバ) の表 | ユーザの表 |
|---|---|---|
| ブロック 0 (`$0000-$1FFF`) | 物理 0 = カーネル (コード、データ、コンソールのリング) | 同じ (どの表にもカーネル) |
| ブロック 1-6 (`$2000-$DFFF`) | 恒等 (サーバのコードとデータ) | プログラム (MM が物理ブロックを割り当てる。48KB) |
| ブロック 7 (`$E000-$FDFF`) | **窓** (カーネルが物理ブロックを割り当てる) | 窓 |
| `$FE00-$FFFF` | 固定 (ベクタ、I/O) | 固定 |
- サーバ (タスク 0-5) は全部システムの表で動く。ユーザのタスクはユーザの表。割り込み・SWI で入るカーネルは、ブロック 0 にあるので、どちらの表でも動ける (FM-11 と同じ考え方)。
- プログラムの領域は 48KB (L1 の 64KB 版の TPA は約 41KB だったので、足りる)。BASIC、jwp、コンパイラも入る見込み。
- 窓は、(1) サーバとユーザのメモリの間のコピー (`mk_copyfrom`/`mk_copyto`、メッセージ)、(2) 新しいタスクへの読み込み (`mk_tload`、`FS_READTL`)、(3) 搭載メモリの検査に使う。
- I/O の番地が `$E000` から `$FF80` に変わる (カーネル、`bsp`、サーバ、ブート)。`IOBASE` として 1 か所にする。

**作り方 (小さな段階に分ける)**
- **3a: 写像の操作を切り出す** (FM-11 だけ。動きは変えない): カーネルの MMU の操作を、`arch/m6809/mmu_fm11.inc` の「マクロ」にまとめる (タスクの切り替え、窓、ページ表の初期化、搭載量の検査)。MM と PM のページの大きさ (4KB) を定数にする。FM-11 Level 2 のテスト (37 項目) が通ること。
- **3b: sbc09 の MMU 版でシェルまで**: `memmap_sbc09_l2.mk`、`arch/m6809/mmu_coco.inc`、`IOBASE`、MK09 用の L2 の ROM イメージ (写像の初期化、ブート、ベクタ)。`sim09 -2` でログインのプロンプトまで。
- **3c: プログラムを動かす**: 窓、`tload`、MM と PM の 8KB のページ。`mk09_test.py` の V2 版を作って、段階 1・2 の機能 (大文字小文字、ログイン、許可) を通す。
- **3d: アプリを全部**: BASIC、jwp、コンパイラ、Pascal。RTC (`date -s`)。FPGA のビットストリームは変えない (実機の確認は別に依頼)。
- 段階 1 と 2 の既存のテストが、このポートの正しさを確かめる役にも立つ。

### 段階 4: カーネルの送信先の表 (MMU のビルドだけ)
- 一般のプログラム (ユーザのタスク) が送れる相手を、TTY、FS、PM、MM に限る (DISK などへの直接の送信を断る)。
- MMU のビルドでは、ユーザのプログラムはメモリと I/O を直接触れないので、これで、サーバを通さずにディスクを触る抜け道がなくなる。
- カーネル版が変わる。`faults` のようなテストを足す。

### 段階 5: 同時に複数端末
- **カーネル**: 受信割り込みのリングを、端末 (線) ごとに持つ (`SYS_RXREG` に線の番号を足す)。通知 (`NFY_RX`) も線ごと。`NTASK` を増やす (いまは 11 で、システム 6 とユーザ 5)。
- **TTY サーバ**: 線の表 (入力のリング、出力、`stty` の状態、文字コードの設定) を持つ。線 0 は、今までの端末 (sbc09: USB シリアルと HDMI、FM-11: 画面とキーボード)。
- **PM**: セッション (線、シェル、前景のプログラム、コンソールの持ち主) を線ごとに持つ。`^C` はその線の前景だけに効く。PM は、`/etc/ttys` に書いた線ごとに `login` を起動し、ログアウトのたびに起こし直す。`ps` に端末を出す。
- **sbc09 の 2 つ目の ACIA**:
  - RTL: `fpga/tn9k/rtl/acia_uart.v` をもう 1 つ追加し、`$E004/$E005` に置く (シミュレータが、すでに `$E004` 以降を 2 つ目以降の ACIA として扱っている (`-net 1=listen:PORT` など) ので、同じ番地にする)。割り込みは IRQ に束ねる。Tang Nano 9K の端子に、UART の TX と RX を足す (制約ファイル `.cst`)。OS-9 と FUZIX が使う他の番地とぶつからないことを確かめる。
  - シミュレータ: すでにある ACIA の追加 (`-net`) を端末として使う。テストの台本から 2 つ目の端末を動かせるようにする (`send2`/`expect2` のようなもの)。
  - Verilator での検証 (既存の検証の流れ)。実機の確認は、Tang Nano 9K と外付けの USB シリアルで行う。
  - **実装済み** (2026-11-23): `sbc09_soc.v` に 2 つ目の ACIA と `rxd1`/`txd1`、`tn9k.cst` のピン 31/32、`scripts/acia1test.s` の Verilator の確認 (`docs/FPGA.md`)。**ピンの確認と実機の試験は、まだ**。
- **FM-11**: 1 つ目は画面とキーボード、2 つ目は **RS-232C のポート** (1 チャンネル)。
  - ドライバ (`bsp/fm11/`) を書く。レジスタの仕様は、`/export/nas/archives/FM-11/docs` の資料と、エミュレータのソースで確かめる。
  - (確認済み: エミュレータの i8251 とホストの pty (`--rsdev`)。**実機の FM-11 には RS-232C のポートが標準で 1 チャンネルある** (ユーザの話))。
  - **エミュレータが RS-232C をモデル化し、ヘッドレスで入力を与えて出力を読めること**が、テストの前提になる。FM-11 の担当 (「FM-11 Debian シミュレータ」のセッション) に、機能の有無と追加を問い合わせる。
  - 仮想コンソール (画面を複数に切り替える) は、今回は作らない。

### 段階 6: 仕上げ
- 文書: `DESIGN.md`、`SPEC.md`、`MANUAL.md`、`README.md`、`fm11/README.md` (2.0 の機能、`/etc` のファイル、`login`、許可)。
- 全テストと `v1guard.sh`。
- FM-11 の担当に、master (2.0 系列) の取り込みと、FM-11 の実機での確認を依頼する。
- FM-11 の実機の確認が済んだら、`2.0.0` に版を上げて確定する。

## 4. 危険と対策

| 危険 | 内容 | 対策 |
|---|---|---|
| sbc09 の MMU 版が大きい | MMU の違い (4KB と 8KB のページ、写像の組が 2 つ、窓の作り方) で、カーネルの MMU の部分を作り直す | 機能を先に FM-11 の Level 2 で作り、テストを揃えてからポートする。FM-11 の既存の MMU 版を、`arch/` の切り出しで壊さないよう、毎回 FM-11 のテストを回す |
| 1.x のビルドを変えてしまう | 共有のソースを触る | `MK09_V2` の条件コンパイルと、`v1guard.sh` のバイト列の比較 |
| FM-11 のエミュレータが RS-232C を持たない | 端末の自動テストができない | 段階 5 の前に、担当へ確認する。必要なら、エミュレータに足してもらう |
| 6809 でのパスワードのハッシュが遅い | ログインが何秒もかかる | 段階 2c の最初に、候補の方式を実測する |
| PC とカードをやり取りする | `foo` と `FOO` は PC では同じ名前。14-15 の領域を PC が作成時に書く | 運用で、同名の大文字小文字違いを作らない。PC が作ったファイルは、21 バイト目が 0 なので、旧ファイル扱いになる |
| カーネルの NTASK 拡大 | TCB の表が増える | MMU のビルドは領域に余裕がある。FM-11 は MMR が 16 組なので、タスクは最大 16 |
| FM-11 の担当の 1.x の変更と衝突する | `kernel.s`、`version.h`、`Makefile` など | 小さな単位で取り込む。衝突しそうなファイルは、事前に連絡する |

## 5. 確認して決めた点
1. `v1guard.sh` の基準は 1.46 (`655ffe5`) とする。
2. 2.0 の MMU 版では BASIC、jwp などのフル版のアプリも動かす (FM-11 Level 2 と同じ構成を目標にする)。
3. 端末の数は、sbc09 が 2 つ (USB シリアル、2 つ目の ACIA)、FM-11 が 2 つ (画面とキーボード、RS-232C)。

なお、段階 5 の前に、FM-11 のエミュレータ担当に RS-232C のモデルとヘッドレスでの入出力を確認する。
