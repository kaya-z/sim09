# MK09 設計書

Copyright (c) 2026 YUKARI Semiconductor Devices

**版: 1.1** (2026-10-19)。ソース (`include/version.h` の `MK09_VERSION`) も同じ版です。変更のたびに両方を上げます (16 章の改版履歴)。

MK09 は MC6809 のための**マイクロカーネル**です。カーネルがするのは、タスクの切り替え、メッセージの受け渡し、タイマ、
メモリの領域の検査だけで、コンソール、ディスク、ファイル、プログラムの読み込みは、メッセージで話す**サーバ**(普通のタスク)がします。
その上で、シェル、コマンド、日本語ワードプロセッサ `jwp` が動きます。

使い方は [MANUAL.md](MANUAL.md)、仕様 (システムコール、メッセージ、形式) は [SPEC.md](SPEC.md) にあります。

> **確認していること / していないこと**
> * `sim09` (6809 のシミュレータ) で、起動、全コマンド、`jwp` (UTF-8 / EUC-JP / Shift_JIS)、SKK 変換、ファイルシステムを自動テストで確認しています (`make test`、mk09_test 69 項目、jwp_test 64 項目、FPGA RTL 上の確認 4 項目、およびファイルシステムの乱数テスト)。
> * Tang Nano 9K の FPGA は、RTL を Verilator で動かしたモデルの上で起動、ファイルの作成、SD カードへの書き込み、電源断を確認しました。
> * **実機の Tang Nano 9K** (2026-10-15): FUZIX 用のビットストリーム (SRAM に書き込み) と SD カードのイメージで、起動からシェルのプロンプトまで動き、
>   `ls` `ps` `df` `date`、ファイルの作成と読み出し、`ipcbench`、`dhry` (最終値の検査 OK)、`jwp` (日本語の入力と保存) を確認しました。HDMI の画面でも、シェルの表示を確認しました。
> * 6809 以外のプロセッサへの移植は、**していません**。移植できるように分けてあり、機械に依存しない C の部分が普通の C コンパイラ (gcc) を通ることだけを確認しています (`tests/portcheck.sh`)。

## 2. 全体の構成

```
 ┌──────────────────────────────────────────────────────────────┐
 │ 利用者プログラム  sh  ls cat cp mv rm mkdir date df ps hd wc   │
 │ (MX 形式)         jwp (日本語ワープロ + SKK)    libmk (C ライブラリ) │
 └───────────────┬──────────────────────────────────────────────┘
                 │ メッセージ (mk_call / mk_callg)  ← 利用者は直接ハードウェアに触らない
 ┌─────────┬─────┴───┬─────────┬─────────┐
 │ TTY     │ DISK    │ FS      │ PM      │  サーバ = ユーザ空間のタスク
 │ コンソール│ SD カード│ FAT16   │ プログラムの │
 │ 行編集   │ 512B 単位│ ファイル  │ 読み込み・終了│
 └────┬────┴────┬────┴────┬────┴────┬────┘
      │ メッセージ │ ・ グラント (指定した範囲のメモリのコピー)
 ┌────┴──────────┴─────────┴─────────┴──────────────────┐
 │ カーネル: タスク、同期メッセージ、通知、タイマ、領域の検査 │
 │   arch/m6809 (SWI、IRQ、RTI)    bsp/sbc09 (ACIA、タイマ、SD) │
 └──────────────────────────────────────────────────────┘
 ブート ROM (256 バイト, $FF00)  →  SD のブートイメージ (カーネル+サーバ)
```

* **サーバとクライアント**: クライアントは `mk_call` でサーバに要求を送り、返事を待ちます。大きなデータは**グラント**で渡します (4.4 節)。
  クライアントが FS に「読め」と頼む → FS が DISK に「ブロックを読め」と頼む → DISK が SD から読んで FS のバッファに写す → FS がクライアントのバッファに写す、という流れで、
  ハードウェアに触るのは DISK と TTY だけです。
* **サーバの置き場所**: サーバはブートイメージに入っていて、起動時に全部がメモリに常駐します。プログラム (`.MX`) は FAT16 のボリュームの `/BIN` から、起動するときに読み込みます。
* **特権**: タスクの作成/終了/書き込み (`mk_tcreate` など) とタイマの購読は、特権のあるタスク (PM と TTY) だけが呼べます。

## 4. カーネル

### 4.1 タスク

タスクは最大 10 (番号 0..9)。0 はアイドル、1..4 は TTY, DISK, FS, PM (起動時に作られる)、5..9 は PM が作る利用者のタスク (シェルと、同時に動く最大 4 つのプログラム)。

各タスクの情報 (36 バイト): 状態、優先度、相手、特権、グラントの権利、終了コード、通知のビット、保存したスタックポインタ、眠りの時刻、
メッセージを受ける番地、メモリの領域 [lo, hi)、グラントの範囲、CPU 時間、送信待ちのメッセージ (10 バイト)。

```
            mk_tstart                  mk_recv / mk_call で待つ                    mk_exit / 検査に違反
  NEW ───────────────▶ READY ◀───────────────────────────────▶ RECV ─────────┐
                      ▲  │ ▲                 相手が送る / 返事が来る            │
         時間片が     │  │ └──────────── SEND ◀── mk_send / mk_call (相手がまだ待っていない)
         切れる      実行 ─────────────▶ SLEEP (mk_sleep)                      ▼
                                                                              ZOMBIE ──mk_treap──▶ FREE
```

### 4.2 メッセージ通信

Minix 3 に似た**同期のメッセージ** (ランデブー)です。システムコールは `send` `recv` `call` `reply` `notify` の 5 つ。

* **`call` = `send` + 返事を待つ**。クライアントは普通 `call` を使います。サーバが `recv` で待っていれば、メッセージはすぐ渡されます。
  待っていなければ、クライアントは SEND の状態で待ち、サーバが `recv` したときに渡されて、返事待ち (RECV) になります。
* **`reply` はブロックしない**。サーバが返事を返すとき、クライアントが待っていなければ (死んだなど) `E_NOTWAIT` を返すだけで、サーバは止まりません。
* **通知**はビットだけの知らせで、ブロックしません。タイマの 1 周期、タスクの終了、`^C` を、TTY/カーネルが PM などに知らせるのに使います。
* **メッセージは 10 バイト**で、固定です。大きなデータは**グラント**で運びます。

### 4.3 割り込みとシステムコールの処理

システムコールは `SWI`、タイマは IRQ です。どちらも CPU が全レジスタ (12 バイト) をそのタスクのスタックに積みます。
カーネルは入口で、積まれた場所 (フレーム) を覚え、**カーネル専用のスタック**に切り替え、処理をして、次に走らせるタスクのフレームを選び、`RTI` で戻ります。
つまり**カーネルはタスクごとのスタックを持たず、処理は割り込みを禁止したまま最後まで走ります**。

* システムコールの番号は A、引数は B / X / Y / U、結果は B (状態) と X (値) です。ブロックするコールは、フレームの B と X を後で書き込むことで完了させます。
* 入口のたびにタスクのスタックポインタが領域の中にあるかを調べ、外なら、そのタスクだけを終了させます (コード `$FD`)。
* 割り込みの出る前の DP レジスタはフレームに入っていて、`RTI` で戻ります。カーネルは自分のページ (変数の 256 バイト) を DP にして直接ページで速くアクセスします。

### 4.4 グラント (大きなデータの受け渡し)

`mk_callg(dst, m, 権利)` は、`m->b` から `m->c` バイトの範囲を、返事が来るまで `dst` が読み書きしてよい範囲として登録します。
サーバは `mk_copyfrom` / `mk_copyto` で、**クライアントのメモリの中のその範囲**に対してだけコピーできます。カーネルは、そのクライアントが本当にそのサーバの返事を待っているか、
権利があるか、範囲に収まるか、サーバ自身のバッファも自分の領域の中かを、毎回検査します。このおかげで:

* サーバが「ほかのクライアントのメモリ」を勝手に触ることはありません (検査は、フラットなメモリでもカーネルがします)。
* **MMU のある機械では、このコピーの 2 つの関数を、アドレス空間をまたいだコピーに差し替えるだけ**で済みます (11 章)。

### 4.5 スケジューラ

* 優先度 (0 が最も急ぐ) が高い READY のタスクを選びます。サーバは 1、利用者は 4、アイドルは 7。
* 同じ優先度どうしは**優先度ごとに「最後に走ったタスク」を覚えて (`rrlast`)、その次から**順番に見ます。時間片は 2 ティック (40ms)。
  (1.0 では「現在のタスクの次から」でした。毎ティックに TTY が起きて走るたびに順番が TTY の位置からやり直しになり、同じ優先度のプログラムが 2 つ以上
  走るときに、番号の大きい方がいつまでも選ばれませんでした。プログラムが 1 つしか走らなかった 1.0 では現れなかった誤りで、1.1 で同時実行を作ったときに見つけました。)
* 速くするため、「前回の選択を変えるようなことが起きていなければ、選び直さない」という印 (`resched`) を持っています。
  誰かが READY になる、時間片が切れる、現在のタスクが止まる、というときだけ全タスクを見ます。
* READY のタスクがなければアイドルが走り、`SYNC` 命令で次の割り込みまで待ちます (シミュレータは、この間 CPU を使いません)。

### 4.6 カーネルの 2 つの実装

| | 6809 アセンブラ (標準) | 移植用の C |
|---|---|---|
| ファイル | `arch/m6809/kernel.s` | `kernel/kernel.c` + `arch/m6809/{arch.h,entry.s,arch.c}` + `bsp/sbc09/bsp.c` |
| 大きさ | **2083 バイト** (コード) + 約 500 バイト (変数) | 3813 バイト + 約 620 バイト |
| メッセージ 1 往復 (クライアント → FS → クライアント) | 約 2.6 ms | 約 5.0 ms |
| 目的 | 64KB の機械でプログラムに広いメモリを残す | 他の CPU への移植の出発点と、アセンブラ版の動作の基準 |

2 つは同じテスト (`tests/mk09_test.py`) を通ります (`make B=build_c KERNEL=c`、`MK09_BUILD=build_c`)。
C 版は `arch.h` の `struct frame` と数個の関数 (`arch_frame_init`、`arch_copy`)、入口のアセンブラ (`entry.s`) だけが CPU に依存します。

## 5. メモリ

6809 の 64KB しかないので、メモリの配分が設計の中心です。

```
$0000-$00FF  使わない (NULL ポインタは無効のまま)
$0100-$010F  ベクタのジャンプ表 (ブート ROM のベクタがここを指す)
$0200-$02FF  ブート ROM のセクタバッファ (起動後は空き)
$0300-$0B4A  カーネル (コード) 2122 バイト
$0B4C-$1417  TTY サーバ (コード) 2251
$1418-$3BEB  FS サーバ (コード) 10195
$3C00-$DFFF  プログラムの領域 (TPA) 41984 バイト = 164 ページ (256 バイト)。メモリ管理 (mm.s) が
             シェルとプログラムに、ページ単位で配る (プログラムは下から、シェルは上から)
$E000-$E1FF  I/O ページ
$E200-$E44F  カーネルの変数、タスク表 (10 タスク)、スタック
$E450-$E60F  TTY のデータとスタック         $E610-$E79F  DISK のデータとスタック
$E7A0-$EF1F  FS のデータとスタック           $EF20-$F0BF  PM のデータとスタック
$F0C0-$F35B  DISK サーバ (コード) 666        $F35C-$FE93  PM サーバ (コード) 2871 (メモリ管理を含む)
$FF00-$FFFF  ブート ROM とハードウェアのベクタ
```

メモリを広く残すためにしたこと:

1. **I/O ページの上 (`$E200-$FEFF`, 約 7KB) にサーバのデータを置く**だけでなく、DISK と PM の**コードも**置く (`memmap.mk` の `HIGH`)。低い側のメモリは TPA が使えます。
2. **カーネルを 6809 のアセンブラで書く** (C 版の約半分)。
3. **シェルを CP/M のコマンドプロセッサのように、TPA の一番上に置き、大きなプログラムが来たら外す**。メモリ管理は、プログラムを下から、シェルを上から割り当てるので、
   空きは真ん中に 1 つにまとまります。`jwp` のような大きなプログラムの空きが足りないとき、PM はシェルを終了させて場所をあけ、プログラムが終わったらシェルを読み込み直します
   (今のディレクトリはファイルシステムが覚えているので変わりません)。小さなプログラム (`ls` や `cp`) では、シェルは外れません。
4. **各サーバのスタックと変数を実測して決めた** (`apps/stk.c` がスタックの使用量を測る。TTY 約 120 バイト、DISK 約 70、FS 約 300、PM 約 120)。
5. **C ライブラリを関数の組ごとに別のオブジェクトにして、使う分だけリンクする** (リンカはオブジェクト単位でしか取り込まないため)。システムコールのスタブは 1 つずつ。
6. **DISK は 256 バイトのバッファ 1 つ**、FS のキャッシュは 512 バイトのブロック 2 つ、PM の読み込みバッファは 128 バイト (起動ブロックと共用)。
7. CMOC に `-fomit-frame-pointer` を付ける (関数ごとの 8 バイトほどの定型処理がなくなる)。
8. 領域の大きさは `tools/fitslots.py` が今のリンク結果に合わせて決め、`tools/chkmap.py` が溢れ (コードやスタックの余裕) を検査する。

結果として、`jwp` (25KB の本体 + 変数 + スタック) のほかに、**文章用のバッファ 11500 バイト**が取れています。

## 6. サーバ

### 6.1 TTY (コンソール)

* ACIA は割り込みを出さないので、**毎ティックと、要求が来るたびに**受信を調べて、128 バイトのリングバッファに入れます。
* **cooked モード** (既定): 行編集をして 1 行ずつ渡します。BS は多バイト文字を 1 文字として消し (UTF-8 の先頭バイトから文字の長さを、EUC-JP/Shift_JIS は規則から)、
  全角は 2 桁戻します。`^U` `^D` `^C`、方向キーの列を読み捨てる、なども。
* **raw モード**: 来ているバイトをそのまま渡す (`jwp` が使う)。`TM_NOWAIT` で待たずに返す。
* 出力は直接 ACIA に書く (送信中は CPU が止まる)。`TM_CRLF` なら LF を CR LF にする。
* `^C` (`TM_ISIG`) を見つけると、PM に通知する。PM はいちばん新しい子プログラムを終了させる。
* 文字コードの設定 (`stty utf8 | euc | sjis`) は、行編集で文字の長さと桁数を数えるために使う。端末側の表示とは無関係です。

### 6.2 DISK

SD カードは 256 バイトのセクタを DMA で読み書きするレジスタ (`$E040..`) を持ちます。DISK は 512 バイトの「ブロック」を 2 つのセクタで読み書きし、
256 バイトのバッファを経由して、クライアントのグラントとの間をカーネルのコピーで写します (DMA でクライアントのメモリに直接書かないのは、MMU のある機械でも同じコードが使えるようにするため)。

### 6.3 FS (ファイルシステム)

* **FAT16** を扱います。MBR から最初の FAT16 のパーティションを探し、そのブートセクタの BPB から配置を求めます。PC で読み書きできるカードになります。
* 名前は 8.3 形式。長いファイル名は作りません (他が作ったものは読み飛ばして、短い名前で見えます)。ディレクトリの作成、削除、名前の変更、
  パスの `.` と `..`、今のディレクトリ (システムに 1 つ、絶対パスの文字列) があります。
* **ブロック番号を 16 ビットに限る**ことで (ボリュームは 32MB まで)、6809 で重い 32 ビット演算を避けています。ファイルの位置と大きさは (ブロック, 端数) の組です。
* **ブロックキャッシュ** 2 つ (最近使っていない方を入れ替え)。書き込みは即座にディスクへ (ライトスルー)。FAT は 2 つとも更新します。
* **連続クラスタの記憶**: ファイルの先頭から連続しているクラスタの長さを覚えて (2 ファイル分)、そこへのシークは FAT をたどらずにします。
  `jwp` は辞書を検索のたびに開き直すので、この記憶がないと、5MB の辞書の二分探索で毎回 FAT を何千回もたどることになります (この記憶を入れる前は、変換 1 回が約 11 秒でした)。
* **機械に依存しない C** (`servers/fs_core.c`) と、メッセージの口 (`fs.c`) に分けてあり、`fs_core.c` はホスト (gcc) 上でも動かせます (`tests/fs_host.c`)。

### 6.4 PM (プロセス管理)

`PM_SPAWN` は、実行ファイル (MX) を読み込んで走らせ、**終わったときに返事を返す** (呼んだシェルは待っているだけで、ブロッキングの呼び出し)。
`PM_SPAWNBG` は同じことをして、**すぐタスク番号を返す** (プログラムは背景で走る。シェルの `コマンド &`)。何本でも (タスクの空きがあるだけ) 同時に走らせられます。

1. ファイルを開き、ヘッダを検査し、必要な大きさ (イメージ + max(bss, 再配置表) + スタック + 起動ブロック) をページ数にして、**メモリ管理に場所を頼む** (6.5 節)。
2. 場所がなければ、頼んだのがシェルのとき**シェルを外して**もう一度頼む (外すのは、頼んだのがシェルのときだけ)。
3. `mk_tcreate` で NEW のタスクを作り、起動ブロックを書き、`mk_tload` でファイルを 128 バイトずつ書き込み、標準入出力のハンドルの持ち主を新しいタスクにし、`mk_tstart`。
   プログラムは**自分で再配置する** (7 章): PM は読み込んだ番地を入口に足すだけで、ファイルの中身は書き換えない。
4. 終了の通知 (`NFY_EXIT`) を受けたら、`mk_treap` で回収して、その持ち主の FS ハンドルを閉じ、**メモリを返し**、前景のプログラムなら頼んだ側に終了コードを返す。
5. **コンソールの持ち主**: キーボードを読めるのは、前景のプログラム (なければシェル) だけです。PM が TTY に `TTYC_SETFG` で知らせ、ほかのプログラムが読むと `E_BUSY`
   (背景のプログラムにキー入力を取られないため)。書き出しは誰でもできます。`^C` は前景のプログラムだけを止めます。
6. `PM_KILL` (背景のプログラムを止める、シェルは不可)、`PM_MEMINFO` (全ページ、空き、いちばん大きい空き、走っているプログラム数)。

PM はシェルの起動と読み込み直しも担当します (シェルが終了しても、すぐ起動し直します。背景のプログラムが走っている間は、外したシェルは待ちます)。

### 6.5 メモリ管理 (MM、PM の中)

「どこに置くか」の方針と、「その範囲の外を触らせない」仕組みを分けてあります。

| 役割 | 担当 | 場所 |
|---|---|---|
| 領域 `[lo, hi)` の保持と検査 (システムコールのアドレス、グラント、スタック) | **カーネル** | `kernel.s` の `uok` `chkstack` `task_create` |
| どのページが空いているか、どこに置くか、足りないときにシェルを外すか | **MM と PM** | `servers/mm.s` `mm.h` / `servers/pm.c` |
| 位置に依存するコードの書き換え | **プログラム自身** (`crt0app.s`) | 7 章 |

MM (`servers/mm.s`) は TPA の 164 ページ (256 バイト) のビットマップで、`mm_alloc(n, top)` (n ページ続きの最初の空きを下から、または上から)、`mm_free`、`mm_info`。
PM が使い、PM 自身の関数呼び出しです。メッセージの窓口は PM が持つ (`PM_MEMINFO`)。
6809 のアセンブラで書いたのは、C だと 400 バイト近くになり、上位メモリ (PM のコードの置き場所) に入らなかったためです。

**MM を別のタスクにするとき**: `mm_*` の呼び出しを `MM_ALLOC` `MM_FREE` `MM_INFO` のメッセージにし (`mm.s` をサーバのメインループで包む)、`TID_MM` を決める。
カーネルの検査は変えなくてよいので、サーバにするのは PM の中の呼び出し 5 か所の置き換えです。上位メモリに空きがないので今は PM の中にあります (本体 2871 バイト、空き 100 バイトほど)。
MMU のある機械では MM が「ページ表を書く特権のシステムコール」を呼ぶ形になります (11.3)。

## 7. プログラムの形式とライブラリ

* **MX 形式 (版 2、位置独立)**: 16 バイトのヘッダ + コード + 初期値のあるデータ + **再配置表**。256 バイトの境界ならどこにでも読み込めます (同時に何本も動かすため)。
  作り方: `tools/mkmx.py` が、同じプログラムを 256 バイトずらした 2 つの番地にリンクし (`Makefile` の `APP`)、2 つのイメージで**違うバイト = アドレスの上位バイト**
  として、その位置の表を作ります (違いが「ちょうど 1」でないバイトがあればエラー)。表は 1 バイトの間隔の並び (1〜254 = そこを書き換える、255 = 254 バイト飛ぶ、0 = 終わり)。
  起動コード (`lib/crt0app.s`) は**位置に依存しない命令だけ**で自分の番地を知り、表をたどって上位バイトに「読み込んだ番地 − リンクした番地」の上位バイトを足し、
  それから bss を 0 にします。表は bss の始まりにあるので、使い終わったら上書きされ、メモリを食いません (実行時の再配置はプログラムが自分でする: PM は小さいまま)。
  スタックと起動ブロック (引数と標準入出力のハンドル) は、PM が領域の最後に用意します。
* **標準入出力**: シェルの `>` `<` は、FS のハンドルを開いて PM に渡します。ハンドルは PM が新しいタスクの持ち物にします。プログラムの中の `read(0)` / `write(1)` が、
  コンソールではなくそのハンドルを使います。
* **ライブラリ `libmk`**: 上の「メッセージを送って返事を待つ」を関数にしたもの (`open` `read` `write` ...、`printf` など)。メモリを節約するため、関数ごとに別のオブジェクトです。

## 8. ブート

```
電源 ─▶ FPGA が PSRAM を 0 にして、ROM ($FF00) から実行開始
     ─▶ ブート ROM: SD のセクタ 2 から順に読み、各セクタの [先頭アドレス][個数][データ] をメモリに写す。個数 0 のセクタの先頭アドレスへジャンプ
     ─▶ カーネル ($0300): ベクタ表 ($0100) を作り、アイドルと 4 つのサーバのタスクを作り、タイマを動かし、最初のタスクを走らせる
     ─▶ FS がボリュームを探して開き (マウント)、PM が /BIN/SH.MX を読み込んでシェルを走らせる
     ─▶ シェルが /ETC/RC.SH を実行し、プロンプトを出す
```

* ブート ROM は **FUZIX のブート ROM と同じ 256 バイト** (`boot/bootrom.s` は `fuzix/bootrom.s` と同じバイト列になる) で、同じ形式のブートイメージを読みます。
  そのため、FUZIX 用に書き込んだ FPGA のビットストリームがそのまま使え、SD カードを替えるだけで MK09 が起動します。
* ブートイメージは `tools/mkimage.py` が、リンクの結果 (S レコード) から作ります。カーネルは `$0300` から、サーバは自分の場所に直接読まれます。
* SD カードの配置は SPEC の 9 章。ブロック 0 の MBR は PC から見えるようにするためのもので、ブート ROM は使いません。

## 9. 日本語の扱い

* コンソールは **8 ビット通し**で、文字コードは TTY の設定 (`stty`) で UTF-8 / EUC-JP / Shift_JIS を選びます。TTY は行編集のためだけにこれを使います。
* **ファイル名**は、8.3 の枠に 0x80 以上のバイトをそのまま入れます (UTF-8 の全角 1 文字 = 3 バイト)。FAT の約束 (大文字化は ASCII だけ) と衝突しません。
  先頭のバイトが `$E5` になる名前は、FAT の約束どおり `$05` で保存します (PC で読むときの扱いは PC の OEM コードページに依ります)。
* HDMI の文字画面 (FPGA) の文字コードは `stty ... hdmi` で切り替えられます。

## 10. 日本語ワードプロセッサ `jwp`

`os9/jwp` (OS-9 用) のソースを `mk09/apps/jwp/` にコピーして、次のように変えました (元のファイルは変えていません)。

| 変更 | 理由 |
|---|---|
| OS-9 のシステムコールの部分 (`sc_*`) を、MK09 の C ライブラリ (`open` `read` `write` `seek` ...) に置き換えた | 移植の本体。`jwp.c` の残りはほぼそのまま |
| 端末の設定を `SS.Opt` ではなく `tty_setmode` で行う | raw モード (反響なし、行編集なし、`^C` もそのまま) |
| **文字コードをビルドごとに 1 つに固定** (`CHARSET=utf8/euc/sjis`)。メッセージと禁則の表は 1 つ分だけ。メッセージは文字列の塊にして、ポインタの表をなくした | メモリ。表が 3 分の 1 になり、ポインタの初期化処理が要らなくなる |
| 辞書やバッファのいくつかを小さくした (1 行 380 バイトまで、候補 48 個まで、キー入力 300 バイト) | メモリ |
| 名前の終わりを CR ではなく NUL に | MK09 のパスの形 |
| 新しいファイルの改行は LF | 普通の文書として |
| 辞書の既定の場所 `/SKK/SKK.DIC` | FAT 8.3 |
| `-fomit-frame-pointer` でコンパイル | 約 500 バイト減る |

* **辞書はディスクのファイル**です。SKK の辞書 (`SKK-JISYO.L`) を `tools/mkskkdic.py` で、読みの順に整列した 1 行 1 語のテキスト (行末 CR) にしたもの (UTF-8 で約 5.6MB)。
  `jwp` は 256 バイトのブロックごとに `seek` と `read` で二分探索をします (メモリには辞書の 1 行分のバッファしかない)。
* 変換 1 回のコストは、二分探索の約 15 回の `seek`+`read` (そのたびにメッセージが FS と DISK を往復する) と、候補の解析です。実測で **約 1.2 秒** (1.8432 MHz の 6809)。
* **文章用のバッファは 11500 バイト** (`JWP_BUF`)。ギャップバッファです。
* 画面の更新は元のまま (変更した行だけを ANSI の制御列で描き直す)。

## 11. 移植性

### 11.1 層

| 層 | 場所 | 内容 | 機械依存 |
|---|---|---|---|
| カーネル | `kernel/kernel.c` | タスク、メッセージ、スケジューラ、グラント | なし (`types.h` の整数型と `arch.h` の 3 つの関数 + フレーム構造体) |
| CPU | `arch/<cpu>/` | トラップの入口、フレーム、コピー | CPU |
| ボード | `bsp/<board>/` | タイマ、電源、時計、SD/ACIA の番地 | ボード |
| サーバ | `servers/` | TTY、DISK、FS、PM | ボードのレジスタは `bsp.h` の名前を通す。ファイルシステムは完全に独立 (`fs_core.c`) |
| メモリの地図 | `memmap.mk` | 領域の大きさ | ボード |
| プログラムとライブラリ | `apps/` `lib/` | | システムコールのスタブ (`lib/mksys.s`) だけが CPU 依存 |

### 11.2 他のプロセッサへ移す手順 (C 版カーネルを使う)

1. `types.h` に整数型を定義する (`u8` `u16` `u32`。ポインタが 16 ビットに収まらない CPU は、`u16` で持っているアドレスを `uptr` に広げる必要がある。メッセージ (`msg_t`) やグラントのアドレスも 16 ビットなので、メッセージの形も変わる)。
2. `arch/<cpu>/arch.h`: `struct frame` (トラップで保存されるレジスタ)、システムコールのレジスタの割り当て (`SC_NR` `SC_B` `SC_X` ...)、`arch_frame_init`、`arch_copy`、`arch_idle_loop`。
3. 入口 (`entry.s` に当たるもの): システムコールと割り込みでフレームを保存し、カーネルのスタックへ切り替え、`k_swi(frame)` / `k_irq(frame)` を呼び、`k_schedule()` が返すスタックポインタに切り替えて復帰する。
4. `bsp/<board>/`: `bsp_timer_start` `bsp_timer_fired` `bsp_power_off`、サーバが使うレジスタ、時計。
5. `lib/mksys.s`: システムコールのスタブ。
6. ブートの方法に合わせて `boot/` を作る。

### 11.3 MMU のある機械にするには

* **領域の検査**は `uok()` / `grant_copy()` / `sc_tload` の 3 か所に集まっています。MMU があるなら、タスクごとに写像を持ち、`uok()` を「そのタスクのアドレス空間で有効か」にし、
  `arch_copy` を「2 つのアドレス空間を一時的に写してコピーする」関数にします。サーバ、プログラム、ライブラリは変わりません
  (サーバが他のタスクのメモリを触るのはグラント経由だけ、DISK も直接 DMA しないため)。
* MX の位置が固定という制約は、MMU があれば、全プログラムを同じ仮想アドレスに置くことで外れます (複数のプログラムが同時に動けます)。
* sim09 の Level 2 (CoCo 3 風 MMU) 版は作っていません。Tang Nano 9K には MMU がないので、この版は 64KB のフラットなメモリで動くことを必須にして作りました。

## 12. 開発で見つかったこと (CMOC と 6809)

6809 用の C コンパイラ CMOC 0.1.100 の癖で、コードが書き換わるまで気づきにくいものです。

* **`unsigned char` どうしの演算は 8 ビットで切れる**: `idx * 32` の結果が 8 ビットで切れ、`idx >= 8` で壊れた (ディレクトリの 9 つ目以降のエントリが見えない)。`(u16)` を付ける。
  同様に `u8 << 8` は 0 になる。
* `cond ? 0 : (unsigned long)` が書けない。`long` の演算は大きなヘルパを呼ぶので、FS はブロック番号を 16 ビットにした。
* 文字列へのポインタの静的な配列は、`--no-relocate` では書けない (文字配列の配列にする)。
* `main` が見えるとスタートアップ (`program_start`、`INILIB`) が付いてしまう。`-Dmain=mk_main` で別名にして、自前の `crt0` を使う。
* リンカはオブジェクト単位でしか取り込まない。関数ごとに別のオブジェクトにする。
* グラントのバッファは、そのタスクの領域の中になければならない。**文字列リテラルはコードの領域にあるので、サーバではそのまま渡せない** (PM は一度データ領域の配列に写す)。
* 6809 の命令: `lwasm` は分岐を自動で長くしないので、`tools/relax.py` で伸ばす。トラップの入口の最初の命令は、タスクの DP のままなので、直接ページの変数に書いてはいけない (拡張アドレスで書く)。
* **`basic` (ソフトウェアの浮動小数点) で見つかったこと**:
  * `unsigned long` の値は、引数でも戻り値でも構造体と同じ扱い (隠しポインタ + `push4ByteStruct`) で、1 回の呼び出しに数百サイクルかかる。32 ビットの加減乗除を C で書くと
    1 回が 4〜13ms (1.8432MHz) になったので、`f_add` `f_mul` `f_div` `f_from_long` は `apps/basic/sfpa.s` に書いた (0.4〜2.4ms)。C 版は参照として残し、
    PC 側の `float` との一致を `tests/sfp_test.c` (乱数 30 万組) で、アセンブラ版を実機相当の環境で `apps/sfptest.c` (300 組の端の例を含む) で確かめる。
  * `return cond ? -(s32)m : (s32)m;` のような `long` の三項演算子や、`if () m >>= n;` (変数での 32 ビット右シフト) で値が壊れることがあった。`if / else` とシフトの関数
    (`shr32` `shl32`) に直した。
  * 構造体の値渡し・値返し (`val expr(void)`) は、式の評価 1 段ごとにコードが膨らみ遅くなる。結果をグローバル変数 (`vt` `vf` `vs`) に置く形にして、コードが約 1.5KB 小さくなった。
  * 式の入れ子 1 段が 100 バイト近くのスタックを使う (再帰下降の 9 段 + 関数呼び出し)。`basic` のスタックは 2300 バイトにしてある (1024 では `INT(-2.5)` で壊れた。
    カーネルのスタック検査は、タスクの切り替えのときにしか働かない)。
  * 速さは、構文の解釈 (1 文あたり約 6k サイクル) が、浮動小数点の計算よりも大きい。`kw()` の連続した比較を、先頭の 1 文字での振り分けにし、変数名と関数名の判定を 1 文字目と 3 文字目の
    確認で先に打ち切るようにして、マンデルブロの描画が 16 分から 8 分になった。

* **同じ優先度のタスクの順番** (スケジューラ): 4.5 節。サーバが毎ティックに起きるので、順番を「現在のタスクから」にしてはいけない。
* **上位メモリがいっぱい**: PM のコードを足す余地がなく、コードを 5% 縮めるために、C の関数呼び出しを減らす・ヘッダの値を `*(u16 *)` で直接読む (6809 は上位バイトが先)・
  メモリ管理をアセンブラにする・時計を FS に移して `rtc.o` を PM から外す (`FS_TIME`)・PM の読み込みバッファと起動ブロックを共用する、をした。
  `tools/fitslots.py` はコードの余裕を 0 にして (下位メモリは TPA のもの)、はみ出したら `make` が止まる。

## 15. 制限と今後

* **MMU がないので、メモリ保護はカーネルの検査だけ**です。プログラムが自分の領域の外を直接書くことは、カーネルには止められません (システムコールに渡すアドレスは検査します)。
* 同時に動くプログラムは、TPA の広さとタスクの数 (シェル + 4) で決まります。画面は 1 つで、背景のプログラムの出力は前景の出力や行編集の途中に混ざります
  (コンソールを分ける仕組みは作っていません)。背景のプログラムはキー入力を読めません。
* ファイルシステムは 32MB まで、8.3 の名前、今のディレクトリは 1 つです。
* 実機の基板では、コンソール (USB シリアル) と HDMI の画面を確認しました (2026-10-15)。HDMI の画面は FPGA の既存の実装のままで、MK09 のために変えたところはありません。
* 作っていないもの: パイプ、複数のコンソール、ネットワーク、ファイル属性の変更、時計の設定、MMU 版。
* ファイルシステムの 6809 版を C ではなくアセンブラで書けば、さらに約 3KB をプログラムに回せます (試作を途中でやめました)。TTY の行編集をクライアント側のライブラリに移せば、約 1KB。
